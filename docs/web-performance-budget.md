# 管理后台性能预算

预算保护真实加载体验，并容纳持续增加的页面与功能。普通构建不更新基线，新增页面不再争用一个固定的“全部共享代码”额度。

## 测量方式

- 首屏：从 Vite manifest 的 `index.html` 出发，只遍历静态依赖，包含 JS 和 CSS。动态加载的页面不计入首屏。
- 按需入口：自动发现所有动态入口，包括服务商等手工分块。计算第一次打开该入口所需的完整静态依赖，扣除已在首屏加载的资源；循环与重复引用不重复计费。
- 全部产物：累计所有实际生成的 JS / CSS，作为趋势参考，不把所有页面的大小简单相加；公共资源只算一次。
- 指标使用生成文件的原始字节数和 gzip 传输字节数。不是 `node_modules` 大小，也不是小程序最终上传包。
- 模块以源文件路径或稳定的手工分块名称标识，文件哈希变化不会清空增长历史。

## 阻断、提醒与余量

| 项目 | 硬限制 | 对比基线的阻断条件 |
| --- | --- | --- |
| 首屏 JS gzip | 96 KiB | 增量超过 `max(8 KiB, 15%)` |
| 首屏 CSS gzip | 16 KiB | 增量超过 `max(2 KiB, 25%)` |
| 单个按需入口新增 JS gzip（含依赖） | 40 KiB | 已有入口增量超过 `max(8 KiB, 50%)` |
| 单个按需入口新增 CSS gzip（含依赖） | 16 KiB | 已有入口增量超过 `max(2 KiB, 50%)` |

这些是本项目的工程保护线，不是通用的浏览器性能保证。迁移时首屏 JS 约72.55 KiB，CSS 约6.73 KiB；JS 硬限制预留约24%的余量，正常的几百字节变化不会触发原先几乎贴线的构建失败。仍需结合实际设备、网络和页面交互验收性能。

接近硬限制80%时提醒。全部 JS 总量较基线增长超过 `max(16 KiB, 20%)`、全部 CSS 增长超过 `max(4 KiB, 25%)` 时只提醒；正常增加独立页面可以继续构建。未在基线中的新入口使用相同的单入口硬限制。

将页面或工作台错误地打入首屏、缺失依赖、损坏或缺失基线，均会失败。不能靠缺失文件、修改哈希、将大依赖移入公共分块绕过统计。

## 日常开发

```bash
cd web
npm run build
```

类型检查、测试、编译与性能检查全部保留。结果为：

- `web/dist/budget.json`：机器可读指标、基线版本、每个入口的依赖和告警。
- `web/dist/budget.md`：首屏、按需入口和与基线的差值表。
- 构建失败日志：具体模块、当前大小、限制或增长量，以及最大的资源文件。

体积超限时仍会生成这两份报告。报告随成功发布的静态产物进入制品，不自动修改 Git 中的 `web/bundle-baseline.json`。

## 有意增加功能时更新基线

先确认增长来自需要的功能、页面仍按需加载、没有误引入整库，完成浏览器回归，再执行：

```bash
npm run budget:baseline -- --reason "Reviewed new editor and verified lazy loading"
```

PowerShell 下如 `npm.ps1` 没有正确传递带空格的参数，使用 `npm.cmd run budget:baseline -- --reason "Reviewed new editor and verified lazy loading"`。

该命令先重新执行测试、类型检查和构建，再用新产物检查绝对性能上限。原因必须填写8到500个字符；记录生成时间、Git 提交和入口指标。绝对上限超出时，不能通过更新基线放行。原因与指标差异应随功能提交，由代码审查确认。

CI 只运行普通 `npm run build`，不要在流水线添加更新基线命令。频繁更新基线而不解释增长，会失去趋势保护。修改硬上限需要设备或网络测量依据，并同步更新此约定。

## 样式加载

模型配置、服务商树及布局、服务接入表单的样式由对应模块导入，不再塞进全局样式入口。公共基础样式仍全局加载。新增页面应沿用页面懒加载和页面内样式导入，并检查首次进入、刷新和多尺寸布局。

小程序保留独立的源码依赖估算与编译流程；此文档的 Web 指标不代替微信开发者工具的最终上传包检查。

# 手机号统一用户

用户主键仍为原 `users.id`，手机号是唯一业务标识。小程序、App、其他端共用用户、积分、订单、作品和服务商关系。不能用客户端传入的用户 ID、手机号或来源直接登录。

唯一性分两个范围：后台账号内部唯一；小程序、App、其他用户端合并唯一。两个范围之间允许相同手机号，例如一个号码可同时拥有一个后台授权账号和一个跨端用户账号。两表各自使用唯一索引，不做跨表排斥；同号关联不会自动授予后台权限。

手机号在所有用户端合并唯一，不按客户端分别注册。微信授权与 App 短信登录并发也解析到同一用户；停用账号继续保留号码，不能改用其他端绕过停用。资料短信验证关闭时也必须保持号码唯一，但未验证资料不能作为跨端登录凭证。数据库唯一索引作为最终约束，撞号返回明确错误。跨端并发登录、资料修改撞号、停用后跨端登录均有回归测试。

## 登录接口

小程序继续调用 `POST /api/auth/wechat`，传微信 `code` 和手机号授权 `phoneCode`。服务端从微信获取手机号后，解析到统一用户；后续微信登录凭证关联该用户。微信支付使用当前微信会话的 OpenID，避免不同微信身份混用。

App / 其他端：

1. `POST /api/auth/phone/code`，请求 `{"phone":"手机号","source":"app"}`。`source` 为 `app` 或 `other`。返回 `challenge`、`expiresIn`（300 秒）、`resendIn`（60 秒），不返回验证码。
2. `POST /api/auth/phone/login`，提交相同的 `phone`、`source`、`challenge` 和六位 `code`。返回 `token`、`userId`、`provider:"phone"`、`expiresIn`、`isNewUser`、`activationRequired`。
3. 后续请求使用 `Authorization: Bearer <token>`，调用 `/api/access` 完成姓名填写及原有开通流程。短信登录不自动开通业务权限。

登录验证码五分钟有效，最多五次错误，成功后原子消费；有 IP、手机号频率限制和每日发送额度。登录始终要求真实短信服务，与“资料填写短信验证”开关独立。开发模式也不回传登录验证码。

仓库目前没有独立 App 客户端工程；上述接口供 App / 其他端接入，现有小程序继续使用微信登录。

## 账号来源与后台授权

新增分公司必须填写负责人手机号（请求 `POST /api/admin/partners` 的顶层 `phone` 字段）。手机号预绑定、分公司和可选后台登录账号在同一幂等事务创建；重复手机号、登录账号或变更重放参数时整体失败。旧分公司没有预留手机号时继续沿用原流程，不猜测绑定。

小程序微信手机号授权或短信验证完成后，预留号码匹配的用户自动获得原分公司的 `partner_owners` 归属，不需要扫码、二次开通；角色使用原分公司节点，原有下级服务商、分佣记录保持不变。首次登录未填姓名时以分公司名称作为初始资料名称，可后续修改。仅手工填写号码、未验证归属时不自动绑定；分公司或预留后台账号被停用、用户已有其他服务商归属时拒绝认领。

手机号绑定复用后台可查看、解除的绑定关系，并记录审计。超管明确解除后，后续登录不会自动恢复。新规则依赖 `branch_phones` 表和 `partners.phone` 字段，部署前需执行既有迁移命令。

复查补充：负责人改号时，在同一事务同步预绑定号码、分公司资料和后台账号，撞号全部回滚；原号码不会继承分公司权限。同一分公司的旧扫码待审核记录会随手机号开通完成审核并更新扫码记录，旧页面不能再次覆盖决定。重试创建请求不覆盖后来重置的密码。注销用户释放号码后，新注册用户不继承历史分公司归属。

分公司未同时开后台登录时，后续补开的账号使用分公司当前手机号，并关联已经完成手机号认领的用户。补开、重新开通账号和手机号归属写入在同一事务中，不能再创建同号的第二个有效后台账号。

分公司手机号流程已通过 Go 全量测试、8 项后台浏览器测试、23 页小程序编译和 50 项登录回归；未操作真实微信模拟器、未部署或执行线上迁移。此增量后 Web 首屏静态依赖仍为 gzip JS 77.88 KiB / CSS 8.84 KiB，全部输出（含异步块）JS 184.72 KiB / CSS 24.79 KiB；性能预算通过，未修改基线。小程序源码依赖估算仍为 720843 字节，微信最终上传包未测量。

`source` 是首次来源，`sources` 是使用过的端，`lastLoginSource` 是最近登录端。枚举为 `miniprogram`、`app`、`other`，用于展示和统计，不作为权限依据。用户管理列表及详情展示来源。

后台账号仍是超管分配的授权和密码凭证，`admin_accounts.userId` 关联统一用户。新建后台账号填写手机号时自动关联；超管也可在“管理账号 → 关联用户”补齐旧账号手机号：已注册且已验证的手机号关联原用户；未注册手机号创建待验证用户，首次用户端登录必须验证手机。一名用户只能关联一个未删除的后台账号。关联不改角色、分佣关系、余额或订单；用户短信 token 无后台权限。

旧后台账号缺手机号时不猜测身份，保留可登录状态，由超管核对后关联。用户端状态和后台授权状态分别管理。普通后台账号仍只能查看下级活动、分佣，以及设置下级算力分佣；本人改密码保留。

后台非空手机号也唯一：平台、服务商及旧的未关联账号共用 `admin_accounts.unique_admin_phone` 数据库约束，停用账号仍占用号码，删除后释放；旧账号未填写手机号可暂时保留。新增、编辑、关联及并发写入重复号码均拒绝。修改关联用户手机号时，同一事务更新后台账号的持久化手机号，任一冲突全部回滚。迁移先按关联用户的实际号码检查重复，不自动删除或覆盖冲突账号。

## 迁移与冲突处理

部署须先停止写入进程，备份数据库，再执行既有 `migrate` 命令，然后启动新版 API。迁移增加凭证表、来源字段和 `users.active_phone` 唯一索引，回填旧账号来源及手机号占用；不重新生成用户 ID，不搬动财务记录。

迁移前检查重复手机号、格式异常及归属冲突，发现后中止并报数量，禁止自行挑选账号覆盖。没有手机号的微信登录资料属于待完成注册状态，不能凭空分配手机号。未验证的旧手机号需要先在原小程序身份中验证，不能仅凭新端输入的手机号占用旧账号。

若两个已经存在的微信用户与同一手机号发生冲突，接口返回 409，保留原记录供超管核对，不自动合并资产。手机号修改仍须经过现有资料验证流程；超管可从用户管理修改，原手机号证明随之清除。删除用户释放手机号，停用用户继续保留手机号。

验证：`go test ./internal/api ./internal/store ./internal/partners`；真实 MySQL 唯一约束用例需要专用 `_test` 数据库的 `MYSQL_TEST_DSN`。未设置时该用例跳过，不代表真实数据库迁移已经验证。

本次本地验证通过 Go 全量测试、11 项后台浏览器回归、小程序 50 项登录测试和 23 页编译。未连接真实短信网关发送短信，未执行业务数据库迁移。

构建报告：Web 首屏静态依赖 gzip 为 JS 77.88 KiB / CSS 8.84 KiB；全部输出（包括异步块）为 JS 184.51 KiB / CSS 24.79 KiB。性能预算通过，原有提醒仍保留，未更新基线。小程序引用源码依赖估算 720843 字节；微信最终上传包未测量，不能以该估算替代。

# 对话模型（DeepSeek、豆包）与按量计费

创作助手（Agent）和「AI写剧本」可以直接调用 DeepSeek 和火山方舟（豆包），不经过中转站。
直连仅限 `chat` 文字回复和创作方案；Agent 确认生成图片或视频时，与创作页共用 `/api/jobs/quote` 和 `/api/jobs`，并只能选择「视频站点配置」同步的创作模型。图片、视频不会由 Agent 直接调用第三方生成接口。

## 配置

后台「系统设置 → 服务接入配置 → 对话模型」，保存后重启服务：

| 配置项 | 说明 |
| --- | --- |
| DeepSeek API 地址 / API Key | 默认 `https://api.deepseek.com` |
| DeepSeek 模型 | 模型 ID，逗号分隔，默认 `deepseek-flash`（能识别图片）；`deepseek-v4-pro` 不能识别图片 |
| 火山方舟 API 地址 / API Key | 默认北京地域；Key 留空时用「视频理解」的 Key |
| 豆包模型 | 方舟已开通的模型 ID 或推理接入点 ID，默认 `doubao-seed-2-1-lite-260915` |

服务启动时，填写的每个模型会登记到「模型管理」（Key 为 `deepseek:模型ID` / `ark:模型ID`；每家第一个模型名称为「DeepSeek」「豆包」，其余为「豆包 模型ID」），
没填 API Key 时显示为不可用。之后改名、排序、上下架、调价都在模型管理里做，重启不会覆盖；
从配置里删掉的模型会变成不可用。「同步上游」只管中转站模型，不会隐藏这些模型。

## 按量（token）计费

模型管理 → 定价（积分 / 千 token，请与服务商官方价同步：1 元 = 10 积分时，官方「元 / 百万 token」÷ 100）：

| 设置 | 说明 |
| --- | --- |
| 输入单价 | 未命中缓存的输入 |
| 缓存命中输入单价 | 服务商从缓存读取的输入（DeepSeek `prompt_cache_hit_tokens`，方舟 `prompt_tokens_details.cached_tokens`）；未设置时同输入单价 |
| 输出单价 | 回复 |
| 高峰时段倍数 | 北京时间工作日 9–12 点、14–18 点，三项单价乘以此倍数（DeepSeek 官方为 2）；1 表示不区分。法定节假日按工作日计 |
| 单次回复上限 | token，默认 4096（约 3000 汉字），发给服务商的 `max_tokens` |

输入、输出单价都为 0 时退回按次计费（基础信息里的消耗积分）。

- 发送时按高峰价预留本轮最多可能消耗的积分：输入按字数计（历史与摘要的上限、每张图 1500 token，长项目另加摘要用量），输出按回复上限。
- 回复完成后按服务商返回的实际 token 扣除（不超过预留），多余部分退回；积分明细备注写明输入、输出、缓存命中 token 和是否高峰。失败全部退回。
  服务商没返回用量（或用户中途停止）时按字数估算。
- 默认单价（新登记的模型，以及仍是旧默认价、未被改过的模型）：DeepSeek Flash 官方 2026-11 价（闲时 输入 ¥1、缓存命中 ¥0.02、输出 ¥4 / 百万 token，高峰 ×2）
  → 0.01 / 0.0002 / 0.04 积分，倍数 2；豆包 Seed 2.1 lite 官方 ¥0.8 / ¥2.7 → 0.008 / 0.027 积分（仍是旧默认 0.008 / 0.02 的会自动改为新价），缓存命中价请按方舟控制台「模型价格」填写。
- DeepSeek 默认模型改为 `deepseek-flash`（官方当前模型名）。新登记的 `deepseek-v4-pro` 默认 0.045 / 0.0015 / 0.135 积分（官方闲时 ¥4.5 / ¥0.15 / ¥13.5），倍数 2，不能识别图片。
- 豆包 Seed 和 DeepSeek 默认开启思考模式（先推理再回答，慢几十秒），请求里统一以 `"thinking": {"type": "disabled"}` 关闭；方舟推理接入点 ID（`ep-…`）沿用接入点自身设置。

小程序 Agent 页输入框上方可切换对话模型，并显示「每轮最多约 X 积分」；按量对话发送时不再逐条弹确认框。

## 流式回复与停止

- 服务端以 `stream: true` 调用模型。同一进程内，回复每变一次就推给读取者；同时最多每 0.2 秒存到 `executions.partial`，供独立 Worker 部署时读取和故障恢复。
- 小程序读 `GET /api/jobs/{id}/stream`（server-sent events，`wx.request` 分块接收）：先收到 `{"text": 已写内容}`，之后是 `{"delta": 新增文字}`，
  结束时 `{"done": true, "status": …}`；一个连接最长 2 分钟，到时发 `{"again": true}` 让客户端重连。nginx 已通过 `X-Accel-Buffering: no` 关闭缓冲。
  基础库不支持分块或连接失败时，自动改为每 0.5 秒读取 `GET /api/jobs/{id}/reply`。
- 小程序把成段到达的文字每 50 毫秒匀速打出（积压越多越快，约 0.3 秒追平），只更新正在写的那条消息，跟随滚动最多每 0.3 秒一次。
- 写到方案代码块时显示「正在整理方案…」，整条回复完成后换成方案卡片；用户上滑阅读时不自动滚动。
- 回复中发送按钮变为「停止回复」（`POST /api/jobs/{id}/stop`，写入 `chat_stops`，任何 Worker 0.5 秒内可见）：
  已写出的内容保留并标注「（已停止回复）」，按字数估算扣费；还没写出内容时本轮失败并全部退回。
- 回复下方的快捷修改（如「缩短到 10 秒」）只在最新一条是方案时出现；提问、分析图片等回复不显示。
- 回复中途断开（没有收到结束标记）、模型中途报错或安全审核拦截时，按失败处理并退回积分，不保留半截方案。

## 上下文与节约 token

- 每轮只带本项目摘要之后的对话（最多 8 轮），从一页（30 条）对话任务里取，不再读取用户的全部任务。
- 长对话自动摘要：摘要之后超过 8 轮、或合计超过 8000 字时，除最近 4 轮外都合并进项目摘要（不超过 300 字，保存在 `agent_sessions.summary`），
  之后每轮带摘要和最近几轮。摘要调用的 token 计入触发它的那一轮。摘要失败时照常发送最近 6 轮。
- 只有最新一版方案完整带上；更早的方案替换成一行“这里给出过方案《标题》，已被后面的版本取代”。
- 每条回复最多 4000 字，所有历史合计最多 8000 字，超出时先丢最早的轮次。
- 历史轮次不再重发图片；本轮只发消息里点名的图片。
- 失败的轮次不进入上下文，修复后（如开通模型）直接重新发送即可继续对话。
- 上一条回复还在写时不能发送下一条（否则新一轮看不到上一条回复）；卡住超过 2 分钟则允许继续发送。
- 模型中途报错或安全审核拦截时，按失败处理并退回积分，提示中文原因。

## 对话里的视频

- Agent 不把原视频直接发给豆包或 DeepSeek 对话模型。视频先交给「视频理解」模型（服务接入配置 → 视频理解，与一键复刻同一个）观看，把概要、开头、结构、风格和分镜台词整理成
  不超过 1500 字的文字交给对话模型。每个视频只看一次，结果存在 `video_notes`（按素材；换了视频理解模型会重新看一次）。多个 Worker 同时要看同一视频时只有一个能调用模型，其他等待结果；失败后 5 分钟内不重复调用。观看时等待提示显示「正在观看视频1…」。
- `CHAT_ARK_MODELS` 和 `VISION_MODEL` 只能填豆包 Seed 对话/理解模型或 `ep-` 接入点；`Seedance` 和 `multi-` 是视频生成配置，保存时会被拒绝，历史误配在启动时会被忽略。
- 视频理解未配置、模型未开通（「视频理解模型不存在或未开通」）、视频超过 512MB（50MB 以上经方舟 Files API 上传后观看）或观看失败时，对话模型会如实告诉用户看不到，而不是凭空回答。
  请在方舟控制台「开通管理」开通 `VISION_MODEL` 填写的模型（默认 doubao-seed-2-1-lite-260915），或改填已开通的支持视频的模型。
- 观看本身目前不单独扣积分；整理出的文字计入这一轮的输入 token。

## 回复内容的各种情况

- Markdown 按纯文本显示：标题、粗体、列表转成普通行；表格转成「A · B · C」行；链接显示为「文字（网址）」；行内代码、代码块去掉反引号保留内容；
  引用的 `>`、分隔线、`<br>`、Windows 换行都会清理。流式输出时只有 ```plan / ```json 代码块会显示「正在整理方案…」，普通代码块照常逐字显示。
- 回复达到「单次回复上限」被截断时，末尾追加「回复达到长度上限……可以说“继续”接着写」；截在方案里时显示「方案没有完整输出 · 重新整理」。
- 逐字显示不会把 emoji 拆成半个字符。
- 本条消息附带的图片会告诉模型其项目编号（「这条消息附带的图片依次是：图片3」），之前各轮的问题注明当时附带了哪些素材（「附带：图片3」，文件不重发），
  方案里的 @图片N 因此对得上。

## 回复不排队

每个进程另有 `CHAT_WORKERS`（默认 2）个只领取对话任务的 Worker，每 0.3 秒查一次；即使 `WORKER_CONCURRENCY` 个通用 Worker 都在等慢图或视频，
Agent 回复也会立刻开始。通用 Worker 照常也会领取对话任务。
